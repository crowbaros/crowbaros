# OAuth Flows and Local Model Runtimes on CrowbarOS Base

**Date:** November 18, 2026
**Issue:** [crowbaros/crowbaros#233](https://github.com/crowbaros/crowbaros/issues/233) (research input to [#237](https://github.com/crowbaros/crowbaros/issues/237), under [#230](https://github.com/crowbaros/crowbaros/issues/230))
**Context:** CrowbarOS runs on a minimal glibc Void Linux Base built without root ([`base/config.json`](../../base/config.json), [`docs/LESSONS.md`](../LESSONS.md)). After Milestone 2, the Desktop ships Fulcrum, the Shell, Studio Settings, and `foot`, with **no browser installed by default** and with Mesa + Void's nonfree `nvidia` driver stack ([`lab/void/config.json`](../../lab/void/config.json), [`compositor-nvidia-2026-11-15.md`](compositor-nvidia-2026-11-15.md)).

## Executive Summary

1. **OAuth on a browserless Desktop is constrained by both protocol and provider Terms of Service.**
   - **GitHub Copilot** is the only major Model provider offering a ToS-compliant, zero-browser **RFC 8628 Device Authorization Grant** for third-party software (via a registered GitHub OAuth App or GitHub App with Device Flow enabled). (Note: **GitHub Models** retired on July 30, 2026.)
   - **OpenAI** offers an official, ToS-compliant open-source third-party flow (**Sign in with ChatGPT** dynamic client registration, no client secret, Responses API access on a ChatGPT plan), **but it strictly requires a local browser and `127.0.0.1` loopback redirect (RFC 8252)**. OpenAI's beta `--device-auth` flow belongs to Codex CLI's first-party sign-in and requires explicit account/workspace opt-in.
   - **Anthropic** and **Google** explicitly **prohibit** third-party Harnesses from offering consumer subscription OAuth (`claude.ai` login or Gemini CLI / `cloudcode-pa.googleapis.com` OAuth). Both direct third-party software to **API keys** (or, for Google, a GCP-project Desktop OAuth client against `generativelanguage.googleapis.com` using loopback redirect). Google's RFC 8628 Device Flow only allows OIDC, narrow Drive, and YouTube scopes—not Gemini or Cloud scopes—and Google retired legacy copy-paste OOB (`urn:ietf:wg:oauth:2.0:oob`) in January 2023.
2. **Before a browser is installed, loopback OAuth cannot finish on-device.** On a bare Milestone 2 Desktop, immediate zero-browser connection options are: **(a) API key** (Anthropic, OpenAI, Google AI Studio, OpenRouter, etc.), **(b) GitHub Device Flow** (display URL/QR + code and approve on a phone), **(c) OpenRouter headless PKCE copy-paste**, or **(d) a local/LAN OpenAI-compatible Model**. Loopback-only OAuth (OpenAI Sign in with ChatGPT, Google Desktop API OAuth) requires either installing a browser first or authenticating on another machine and transferring the credential file.
3. **Void Linux's official `current` repository packages neither `llama.cpp`, `ollama`, `vllm`, nor NVIDIA's CUDA Toolkit (`cuda`).** Verified directly against `repo-default.voidlinux.org/current/x86_64-repodata` and `void-linux/void-packages`: `llama.cpp` PRs ([#59027](https://github.com/void-linux/void-packages/pull/59027), [#60782](https://github.com/void-linux/void-packages/pull/60782)) were closed unmerged (Void maintainers cited hourly/daily release churn), `ollama` remains an open request ([#50094](https://github.com/void-linux/void-packages/issues/50094)) with closed PRs ([#48199](https://github.com/void-linux/void-packages/pull/48199), [#54155](https://github.com/void-linux/void-packages/pull/54155), [#62417](https://github.com/void-linux/void-packages/pull/62417)), and CUDA Toolkit ([#20077](https://github.com/void-linux/void-packages/issues/20077)) is unpackaged. CrowbarOS cannot rely on upstream `xbps-install llama.cpp` or `xbps-install ollama`.
4. **Vulkan is the single right local GPU backend on Void Base.** Milestone 2's Void stack **already carries Vulkan**: [`lab/void/config.json`](../../lab/void/config.json) already installs `vulkan-loader` (0.57 MiB installed) for GPUI/`blade`, Void's `mesa` provides `mesa-vulkan-radeon` (18.50 MiB) and `mesa-vulkan-intel` (44.57 MiB), and Void's nonfree `nvidia` 595.112.07 package already installs `usr/share/vulkan/icd.d/nvidia_icd.json` alongside `libcuda.so.1` (driver only—no `nvcc`/`libcudart`/`libcublas`/`libnvrtc`). Upstream `llama.cpp` (`b12531`) Vulkan Linux binaries are **35.3 MiB compressed**, versus **641–780 MiB** for `llama.cpp` CUDA or **1,474.2 MiB compressed** for Ollama's Linux tarball, and all Void build dependencies for `llama.cpp -DGGML_VULKAN=ON` (`cmake`, `gcc`, `vulkan-loader-devel`, `Vulkan-Headers`, `SPIRV-Headers`, `shaderc`) live in Void's `current` repo for rootless builds.
5. **Do not bundle a local runtime or Model weights in Base.** Even a small 4B–9B Q4 vision + tool-calling Model plus its `mmproj` projector occupies **4.8–6.4 GiB on disk** and needs **6–10 GiB VRAM/RAM**, while strong 24B–35B Models take **14–22 GiB on disk** and **16–28 GiB VRAM/RAM**—exceeding Base's 4–6 GiB root disk and 2–4 GiB VM RAM ([`base/config.json`](../../base/config.json), [`lab/void/config.json`](../../lab/void/config.json)). Supporting an **OpenAI-compatible endpoint** (local or LAN) as a first-class Model provider costs Base nothing and pairs cleanly with optional on-demand installation of a pinned Vulkan `llama.cpp` (`llama-server`) runtime.

## 1. OAuth Flows on a Minimal Desktop

### 1.1 Standards Baseline: RFC 8252 vs. RFC 8628

Two IETF standards govern native/CLI OAuth sign-in:

- **RFC 8252 — OAuth 2.0 for Native Apps** ([`datatracker.ietf.org/doc/html/rfc8252`](https://datatracker.ietf.org/doc/html/rfc8252)):
  - **External user-agent requirement (Section 8.12):** Native apps MUST use the external system browser rather than an embedded webview so the app cannot inspect credentials and so the person reuses existing browser sessions and passkeys/MFA. For CrowbarOS, this also rules out embedding a heavy WebKit/Chromium webview in the Shell solely for OAuth.
  - **Loopback interface redirection (Section 7.3):** The native app binds an ephemeral port on `http://127.0.0.1:<port>/...` (or `[::1]`), opens the authorization URL in the local browser with PKCE (RFC 7636), and receives `?code=...&state=...` when the authorization server redirects the browser back to loopback. **Failure mode without a local browser:** a browser on a phone or second computer cannot reach the CrowbarOS machine's `127.0.0.1`.
- **RFC 8628 — OAuth 2.0 Device Authorization Grant** ([`datatracker.ietf.org/doc/html/rfc8628`](https://datatracker.ietf.org/doc/html/rfc8628)):
  - Built specifically for browserless or input-constrained devices. The client POSTs to the device authorization endpoint (Section 3.1), displays a short `verification_uri` (plus optional QR code for `verification_uri_complete`, Section 3.3.1) and short `user_code`, and polls the token endpoint with `grant_type=urn:ietf:params:oauth:grant-type:device_code` (Sections 3.4–3.5) until the person approves on a phone or another computer.
  - **Security caveat (Section 5.4 — Remote Phishing):** Because no redirect URI binds the browser to the requesting machine, device codes can be phished. Providers therefore restrict or disable Device Flow by default (see OpenAI and Google below).

### 1.3 Provider Deep Dives

#### Anthropic (Claude)
Under *Authentication and credential use* in [Claude Code Legal and Compliance](https://code.claude.com/docs/en/legal-and-compliance#authentication-and-credential-use):
- *"OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Ultra, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications."*
- *"Developers building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication through Claude Console or a supported cloud provider. Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow."*
- Anthropic does allow preinstalling/running the **unmodified** Claude Code binary in third-party products under Commercial Terms if no built-in auth method is disabled and each person authenticates directly ([Can customers offer Claude Code in their products?](https://code.claude.com/docs/en/legal-and-compliance#can-customers-offer-claude-code-in-their-products)). For CrowbarOS's own Harness, however, direct Anthropic integration must use **API keys** (`ANTHROPIC_API_KEY` from Claude Console) or cloud providers (Bedrock, Vertex, Foundry).

#### OpenAI (Sign in with ChatGPT & Codex)
OpenAI is the notable exception among frontier labs in publishing an official open-source OAuth path for consumer subscriptions:
- **Sign in with ChatGPT — Open-Source Plan Usage** ([overview](https://developers.openai.com/siwc/token-sharing-open-source), [registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference), [preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)):
  - Public client (no client secret). The app persists a stable opaque `ext_agent_host_id` (e.g., `urn:uuid:...`), binds a loopback callback listener (`http://127.0.0.1:<port>/auth/callback` or `localhost`), and sends the person's browser to `https://auth.openai.com/api/accounts/authorize` with `client_id=dynamic_agent_client`, `agent_name_hint`, PKCE (`S256`), `nonce`, `state`, `resource=https://api.openai.com/v1`, and scopes `openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`.
  - The callback returns an account- and workspace-bound `client_id` (`oaiapp_...`) and authorization `code`, exchanged at `https://auth.openai.com/api/accounts/oauth/token` for rotating `access_token` / `refresh_token` / `id_token` (stored `0600`).
  - Inference calls `https://api.openai.com/v1/responses` with `Authorization: Bearer <access_token>`, `store: false`, and `stream: true`.
  - **Browser requirement:** OpenAI's [Self-hosted VMs guide](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms) explicitly states: *"A `127.0.0.1` callback reaches the computer running the browser, not the remote VM. Complete OAuth locally with the same tool/client... Transfer the selected registration's protected credential file."* There is **no** RFC 8628 device flow in the open-source SIWC spec.
- **Codex CLI `--device-auth` (Beta):** Documented at [Codex Authentication](https://developers.openai.com/codex/auth) and implemented in [`codex-rs/login/src/device_code_auth.rs`](https://github.com/openai/codex/blob/main/codex-rs/login/src/device_code_auth.rs) (`POST /deviceauth/usercode`, polling `POST /deviceauth/token` for up to 15 minutes). It requires the person (or workspace admin) to opt into device code login in ChatGPT security settings, and is wired to Codex CLI's own login rather than dynamic third-party client registration.

#### Google (Gemini)
- **RFC 8628 Device Flow is blocked for Gemini scopes:** [OAuth 2.0 for TV and Limited-Input Device Applications](https://developers.google.com/identity/protocols/oauth2/limited-input-device#allowedscopes) restricts `https://oauth2.googleapis.com/device/code` strictly to `openid`, `email`, `profile`, `drive.appdata`, `drive.file`, `youtube`, and `youtube.readonly`. Requesting `cloud-platform` or `generative-language` fails.
- **OOB copy-paste is dead:** Google deprecated `urn:ietf:wg:oauth:2.0:oob` for all production clients on January 31, 2023, directing desktop apps to the **loopback IP address flow** ([OAuth 2.0 for Desktop Apps](https://developers.google.com/identity/protocols/oauth2/native-app)).
- **Gemini CLI OAuth is prohibited for third-party Harnesses:** While `google-gemini/gemini-cli`'s [`oauth2.ts`](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/code_assist/oauth2.ts) implements both loopback (`http://127.0.0.1:<port>/oauth2callback`) and a `NO_BROWSER=true` copy-paste fallback (`https://codeassist.google.com/authcode`), Google's [Gemini CLI Terms of Service](https://geminicli.com/docs/resources/tos-privacy/) states verbatim: *"Directly accessing the services powering Gemini CLI (for example, the Gemini Code Assist service) using third-party software, tools, or services (for example, using OpenClaw with Gemini CLI OAuth) is a violation of applicable terms and policies. Such actions may be grounds for suspension or termination of your account."*
- **Official third-party paths:** An **AI Studio API key** or a **GCP Desktop OAuth client** against `generativelanguage.googleapis.com` ([Gemini API OAuth](https://ai.google.dev/gemini-api/docs/oauth)), which requires a Google Cloud project (`x-goog-user-project`) and loopback redirect (local browser).

#### GitHub Copilot
- **Native RFC 8628 Device Flow:** [Authorizing OAuth apps — Device flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#device-flow) supports `POST https://github.com/login/device/code` and polling `POST https://github.com/login/oauth/access_token` with a 15-minute user code lifetime, no client secret required, and optional expiring tokens (8-hour access token + 6-month refresh token via `offline_access` or app setting).
- **Third-party support:** GitHub's [Copilot SDK Authentication](https://docs.github.com/en/copilot/how-tos/copilot-sdk/auth/authenticate) and [GitHub OAuth setup](https://docs.github.com/en/copilot/how-tos/copilot-sdk/setup/github-oauth) explicitly document authenticating people via GitHub OAuth device flow or a registered GitHub OAuth App / GitHub App (`gho_`/`ghu_` tokens).
- **Retirement note:** GitHub's standalone **GitHub Models** inference service retired on July 30, 2026; third-party integrations now go through Copilot or BYOK providers.

#### OpenRouter (Aggregator Pattern)
- [OpenRouter OAuth PKCE](https://openrouter.ai/docs/guides/overview/auth/oauth#headless-apps-ssh-servers-containers) lets any app generate a PKCE challenge, send the person to `https://openrouter.ai/auth?code_challenge=...&code_challenge_method=S256` (either with a `localhost` `callback_url` or **without** `callback_url` for headless copy-paste), and exchange the returned code for a person-controlled API key—providing a browserless, ToS-clean single integration across Claude, OpenAI, Gemini, and open-weights Models.

### 1.4 Browserless Desktop UX & CrowbarOS Security Lessons

Because Base ships without a browser after Milestone 2:
1. **Never assume a browser is present when configuring a Model.** The Shell's Model setup UI must inspect whether a default browser handler exists (`xdg-open` / desktop entry) before offering loopback OAuth flows:
   - **Works immediately with zero browser:** API key entry (paste/type), GitHub Device Flow (render short URL + QR code + 8-character code directly in the Shell so the person scans it on their phone), OpenRouter headless PKCE (URL + QR + paste code), and local/LAN OpenAI-compatible servers.
   - **Requires a browser (or second machine):** OpenAI Sign in with ChatGPT and Google Desktop API OAuth. Without a browser, the Shell must either (a) offer a one-click path to install a browser via `xbps`, or (b) clearly explain credential import from another machine rather than failing silently or hanging on `Waiting for callback on 127.0.0.1:...`.
2. **Respect `docs/LESSONS.md`:**
   - **Secrets stay out of the Agent's context (ADR 0008):** OAuth token exchange, refresh, and API key storage (`0600` files owned by the Harness credential service) must run in Shell/Harness code outside the Model's prompt, transcript, and tool output.
   - **Agents never drive the person's browser (ADR 0013):** The Shell—triggered directly by the person's click/keystroke—launches `xdg-open` for loopback OAuth or renders the Device Flow URL/QR code; the Agent never automates sign-in pages.

### 2.2 Why Vulkan Aligns Uniquely with Milestone 2's Mesa + NVIDIA Stack

Inspecting [`srcpkgs/nvidia/template`](https://github.com/void-linux/void-packages/blob/master/srcpkgs/nvidia/template) and [`srcpkgs/mesa/template`](https://github.com/void-linux/void-packages/blob/master/srcpkgs/mesa/template) reveals a clean architectural fit:

- **One backend across AMD, Intel, and NVIDIA:** Void's `nvidia` package installs `usr/share/vulkan/icd.d/nvidia_icd.json` and `libnvidia-glvkspirv.so` out of the box. Mesa provides `mesa-vulkan-radeon` (AMD) and `mesa-vulkan-intel` (Intel), and CrowbarOS's graphical guest **already installs `vulkan-loader`** for GPUI (`blade`). A single Vulkan inference binary accelerates across all three GPU vendors without bundling proprietary CUDA or ROCm toolkits.
- **Dramatic binary size difference** (measured from official GitHub releases on November 18, 2026):
  - **`llama.cpp` `b12531` Vulkan x86_64** ([release `b12531`](https://github.com/ggml-org/llama.cpp/releases/tag/b12531)): `llama-b12531-bin-ubuntu-vulkan-x64.tar.gz` = **35.3 MiB compressed** (CPU-only `llama-b12531-bin-ubuntu-x64.tar.gz` = **22.8 MiB**).
  - **`llama.cpp` `b12531` CUDA x86_64**: `llama-b12531-bin-ubuntu-cuda-13.5-x64.tar.gz` (**217.5 MiB**) + `cudart-llama-b12531-bin-ubuntu-cuda-13.5-x64.tar.gz` (**423.5 MiB**) = **641.0 MiB compressed** (CUDA 12.8 = **779.6 MiB compressed**), and NVIDIA-only.
  - **`llama.cpp` `b12531` ROCm x86_64**: **270.6 MiB compressed**, plus external ROCm runtime that Void does not package.
  - **`ollama` `v0.40.16` Linux x86_64** ([release `v0.40.16`](https://github.com/ollama/ollama/releases/tag/v0.40.16)): `ollama-linux-amd64.tar.zst` = **1,474.2 MiB compressed** (bundles CUDA + Vulkan + CPU runners), plus `ollama-linux-amd64-rocm.tar.zst` = **1,005.1 MiB compressed** for AMD ROCm.
- **Linux operational notes for Vulkan & NVIDIA:**
  - **Device permissions:** The local Model runner process needs access to `/dev/dri/renderD*` (typically via `render` / `video` group membership; see [Ollama `docs/gpu.mdx`](https://github.com/ollama/ollama/blob/main/docs/gpu.mdx)).
  - **Multi-GPU selection:** Both `llama.cpp` and Ollama honor `GGML_VK_VISIBLE_DEVICES` (e.g., selecting a discrete GPU over an integrated GPU, or `-1` to disable Vulkan).
  - **VRAM reporting in Ollama:** Ollama's Vulkan scheduler requires `setcap cap_perfmon+ep` on the `ollama` binary to read exact available VRAM without root; otherwise it falls back to approximate model-size heuristics ([Ollama `docs/gpu.mdx`](https://github.com/ollama/ollama/blob/main/docs/gpu.mdx)).
  - **NVIDIA suspend/resume:** Ollama documents a Linux NVIDIA suspend/resume issue where `nvidia_uvm` can lose GPU discovery ([`docs/gpu.mdx`](https://github.com/ollama/ollama/blob/main/docs/gpu.mdx)). CrowbarOS already sets `NVreg_PreserveVideoMemoryAllocations=1` for Fulcrum on Void ([`compositor-nvidia-2026-11-15.md`](compositor-nvidia-2026-11-15.md)); Vulkan avoids the CUDA UVM path altogether, though any local inference service still needs VRAM reload/eviction testing across `zzz` suspend/resume.

### 2.3 Runtime Comparison & Rootless Build Feasibility

| Dimension | `llama.cpp` (`llama-server`) | `ollama` (`ollama serve`) |
| --- | --- | --- |
| **License & implementation** | MIT, C/C++ ([`ggml-org/llama.cpp`](https://github.com/ggml-org/llama.cpp)) | MIT, Go + CGo/GGML ([`ollama/ollama`](https://github.com/ollama/ollama)) |
| **Void `xbps` package** | None | None |
| **Rootless build on Void** | **Clean & small.** Per [`docs/build.md`](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md), `cmake -B build -DGGML_VULKAN=1` needs only Void's `cmake`, `gcc`, `vulkan-loader-devel`, `Vulkan-Headers`, `SPIRV-Headers`, and `shaderc` (`glslc`)—all in Void's `current` repo, zero root, zero CUDA SDK. | **Possible (`-DOLLAMA_LLAMA_BACKENDS="vulkan"`)** per [`docs/development.md`](https://github.com/ollama/ollama/blob/main/docs/development.md), requiring Go + CMake + Vulkan dev deps, or extracting upstream's 1.47 GiB `tar.zst` tarball. |
| **Init / service model** | Plain foreground binary (`llama-server --host 127.0.0.1 --port ...`)—trivial `runit` service. | Upstream [`docs/linux.mdx`](https://github.com/ollama/ollama/blob/main/docs/linux.mdx) assumes `systemd`; requires a custom `runit` service on Void. |
| **OpenAI API + Vision + Tools** | Native `/v1/chat/completions`, multimodal via `libmtmd` (`--mmproj` or `-hf`, [`docs/multimodal.md`](https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md)), tool calling via `--jinja` ([`docs/function-calling.md`](https://github.com/ggml-org/llama.cpp/blob/master/docs/function-calling.md)). | Native `/v1/chat/completions` and `/api/chat`, built-in model registry (`ollama pull`), automatic `mmproj` & tool-template packaging. |
| **Model management UX** | Raw GGUF + `mmproj` files (or `-hf org/repo:quant` direct pull). | Polished single-name pull (`ollama pull qwen3.5:9b`) and automatic model load/unload lifecycle. |

**Rootless packaging takeaway:** Because Void does not package either runtime, CrowbarOS has two clean rootless options if it provides an on-demand local runtime:
1. **Build `llama.cpp` (Vulkan) rootless in CI / `void_base.py`** from a pinned tag using Void's `current` build packages (`cmake`, `gcc`, `vulkan-loader-devel`, `Vulkan-Headers`, `SPIRV-Headers`, `shaderc`), shipping a ~35 MiB artifact (or CrowbarOS-signed `.xbps` package).
2. **Download a pinned, SHA-256-verified upstream release archive** on demand (mirroring how [`base/void_base.py`](../../base/void_base.py) pins `xbps-static` by SHA-256), avoiding any Base image bloat.

## 3. Packaging, Footprint, and Local Vision + Tool-Calling Models

### 3.1 Packaging & Deployment Tradeoffs

| Strategy | Added Base Disk | Added Base Idle RAM | Works in 4 GiB VM / Weak Laptop? | UX Tradeoff |
| --- | --- | --- | --- | --- |
| **A. Ship local runtime in Base** (`llama-server` Vulkan vs. Ollama) | ~90–120 MiB (`llama.cpp` Vulkan) or ~4+ GiB (Ollama); **still 0 Models included** (weights are 5–20+ GiB) | 0 MiB when stopped; 6–28+ GiB when Model loaded | Runtime installs, but Model weights won't fit Base's 4–6 GiB root disk and CPU/Lavapipe inference is impractically slow | Pays maintenance & update churn on every Base build (even for people using cloud APIs or LAN servers), and still requires downloading multi-GB weights on first use. |
| **B. Install runtime on demand** (CrowbarOS-managed download or CrowbarOS `.xbps` repo + `runit` service) | **0 MiB** in Base | **0 MiB** until opted in | Only installed on machines with sufficient disk + Vulkan GPU / RAM | Keeps Base small ([`docs/VISION.md`](../VISION.md)); the person opts in via Studio Settings / Agent setup, downloads the pinned Vulkan runtime + chosen GGUF/`mmproj`, and gets a managed local daemon. |
| **C. Connect to local or LAN OpenAI-compatible server** (`http://<host>:<port>/v1`) | **0 MiB** in Base | **0 MiB** | **Yes** (offloads inference to a LAN workstation/DGX/Mac/server, or connects to a locally installed `llama-server` / `ollama`) | Zero Base footprint, works immediately in VMs and thin laptops, and uses the exact same OpenAI-compatible client path that Option B speaks to on `127.0.0.1`. |

Notice that **Option C is the foundation of Option B**: if the Harness natively supports configurable OpenAI-compatible endpoints (URL + optional bearer token + vision/tools capability flag), then both LAN servers (e.g., a workstation running `llama-server`, `ollama`, or `vllm`) and an on-demand local `llama-server` (`http://127.0.0.1:8080/v1`) share one wire protocol.

**Practical realities for Milestone 3:**
1. **Disk and VRAM floor:** Base's current VM disk is 4 GiB ([`base/config.json`](../../base/config.json)) and graphical guest disk is 6 GiB with 4 GiB RAM ([`lab/void/config.json`](../../lab/void/config.json)). Even the smallest genuinely capable vision + tool-calling Models (`Gemma 4 E4B`, `Qwen3-VL 8B`, `Qwen3.5 9B`) need ~5–6.5 GiB of disk just for weights plus 8–12 GiB VRAM/RAM, while dependable multi-step OS tool calling with screenshots realistically lives in the **24B–35B tier** (14–22 GiB disk, 16–24+ GiB VRAM—or a LAN box).
2. **VRAM contention with Fulcrum and GPUI:** Fulcrum and the GPUI Shell share GPU VRAM with any local Model. An 8–12 GiB GPU running a 4K/6K display plus a 6 GiB Model and vision KV cache can easily hit OOM/eviction unless context size and screenshot resolution are bounded.
3. **Screenshot resolution & `mmproj` hygiene:** High-resolution desktop screenshots (e.g., 3840×2160 or 6144×2560 from [`compositor-nvidia-2026-11-15.md`](compositor-nvidia-2026-11-15.md)) explode visual token counts and KV memory on local VLMs; downscaling/cropping captures before sending matters far more for local Models than for cloud Models. In `llama-server`, both `--jinja` (for native tool-call parsing) and `--mmproj` (or `-hf` auto-discovery) must be enabled.

## 4. Key Inputs for Decision Ticket `#237`

These primary-source findings narrow the design space for [#237](https://github.com/crowbaros/crowbaros/issues/237):

1. **Auth tiering on a browserless Desktop:**
   - **Day-one, zero-browser paths:** API keys (Anthropic, OpenAI, Google AI Studio, OpenRouter) + OpenAI-compatible local/LAN endpoints + **GitHub Device Flow** (RFC 8628, QR/URL + code on a phone) + optional OpenRouter headless PKCE.
   - **Browser-dependent OAuth:** **OpenAI Sign in with ChatGPT** (official open-source dynamic client registration) is the clearest ToS-compliant consumer-subscription OAuth path, but strictly needs a local browser (`127.0.0.1` loopback) or credential import from another machine. Do **not** build third-party subscription OAuth shims for Anthropic `claude.ai` or Google `cloudcode-pa`, as both violate provider ToS and risk suspending the person's account.
2. **Local Models architecture:**
   - **Do not ship a local runtime or weights in Base.** Void does not package `llama.cpp` or `ollama`, Ollama's Linux bundle is 1.47 GiB compressed, and Model weights dwarf Base.
   - **Make OpenAI-compatible endpoints (local/LAN) first-class**, and if Milestone 3 (or a follow-on) offers one-click local Models on bare metal, target **`llama.cpp` (`llama-server`) with Vulkan**—either built rootless from Void's `current` Vulkan dev packages or fetched as a SHA-256-pinned ~35 MiB upstream Vulkan archive—reusing Milestone 2's existing `vulkan-loader` + Mesa/NVIDIA ICD stack across AMD, Intel, and NVIDIA without CUDA or ROCm.
3. **VM & offline behavior ("life without a Model"):**
   - Because Milestone 2's QEMU VM has 4 GiB RAM and software Vulkan (`mesa-vulkan-lavapipe`), local vision+tool Models will not be usable inside default VMs; CrowbarOS's unconfigured/offline Desktop state and LAN endpoint support are essential for both real hardware without a GPU and VM development/testing.
